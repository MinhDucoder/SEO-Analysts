01 · Vấn đề

Công cụ SEO hiện tại thiếu gì?

Quá đắt

Ahrefs, SEMrush: $99–449/tháng. Vượt ngân sách cá nhân và SME.

Quá giới hạn

Free tools: 1–3 audit/tháng, không export PDF, không lưu lịch sử để compare.

Quá hẹp

Lighthouse chỉ đo performance, không có rule SEO chuyên sâu, không share được.

Khoảng trống → cần một SaaS tự host được, có đủ rule SEO + Core Web Vitals + share + compare, vận hành dưới $40/tháng.
Ba gap rõ: giá, giới hạn audit, và scope. Lighthouse built-in của Chrome tốt về performance nhưng không chấm SEO theo rule và không lưu lịch sử.
02 · Giải pháp — What

SEO Analysts làm được gì?

  • Crawler thực sự — Cheerio default, fallback Playwright nếu trang là SPA.
  • 22 SEO rules custom, mỗi rule có weight cấu hình được live qua admin API.
  • Core Web Vitals qua Lighthouse — chiếm 30% tổng điểm.
  • Keyword analysis — TF, density, placement (title / H1 / URL / 100 từ đầu).
  • PDF report + share link công khai — token 64 ký tự hex, revoke được.
  • Compare 2 audits cùng domain để theo dõi tiến triển theo thời gian.
Nói nhanh 6 features. Nhấn điểm 1 (Playwright fallback) và điểm 6 (compare) — đây là 2 thứ tool free thường không có.

04 · Triết lý — Why

Orchestration + Choreography

Orchestration (cứng) — khởi đầu

Gateway cầm trịch: validate request, auth, rate-limit, enqueue. Một điểm vào duy nhất → dễ kiểm soát security + consistency.

Choreography (mềm) — xử lý

Workers tự diễn qua BullMQ + Pub/Sub. Không service nào "ra lệnh" — analyze + keyword tự chạy song song, report tự lắng nghe event.

Vì sao hybrid? Khởi đầu cần validation tập trung → chọn orchestration. Xử lý cần scale độc lập và loose coupling → chọn choreography. Pattern này được khuyến nghị trong Building Event-Driven Microservices (Bellemare, O'Reilly 2020) cho workload có bước khởi đầu cần gate tập trung.
Đây là điểm nhấn số 1 của deck. Nhiều project sinh viên chọn 1 trong 2 thuần — ở đây mình chọn kết hợp vì đó là realistic pattern. Dừng 30 giây ở slide này.
05 · Services · 1/5

Gateway

HTTP :3000 · gRPC client :50051

Cổng vào duy nhất. Chỉ service này expose ra public.

What · trách nhiệm

  • Auth: register, login, JWT + refresh rotation, Google OAuth, verify email
  • REST /api/v1/{auth,audits,users,admin,shared}
  • Socket.IO /ws — đẩy progress real-time
  • Orchestrator: nhận POST audit → enqueue crawl.start
  • Rate-limit Redis (audit/hour, login/15min)

Why · quyết định thiết kế

  • Chỉ Gateway public → giảm attack surface; service khác không cần auth nội bộ.
  • Refresh token rotated + hashed (OWASP) → an toàn trước XSS/CSRF cơ bản.
  • Cookie HTTP-only scope hẹp /api/v1/auth → không bị JS đọc được.
  • SSRF validator trước khi enqueue → chặn private IP từ URL input.
Auth làm đúng chuẩn OWASP chứ không dừng ở "JWT-trong-localStorage" như nhiều project. Điểm này hội đồng hay hỏi về security.
05 · Services · 2/5

Crawler

gRPC :50052 · stateless · cache Redis 1h

Lấy dữ liệu trang, đo Core Web Vitals, fan-out analysis.

What · trách nhiệm

  • Consume crawl.start
  • Cheerio fetch HTML → detect SPA → fallback Playwright
  • Lighthouse Programmatic API → LCP, CLS, INP, TBT
  • PageDataExtractor chuẩn hoá data cho downstream
  • Fan-out → analyze.start + keyword.start
  • Pub audit.progress, crawl.done

Why · quyết định thiết kế

  • Cheerio default + Playwright fallback → nhanh cho trang tĩnh, đúng cho SPA. Không tốn RAM 200MB cho mọi request.
  • Browser pool (BROWSER_POOL_SIZE) → tránh cold-start Playwright → tiết kiệm 2–3s/audit.
  • Stateless → scale ngang tự do, không cần DB.
  • Cache Redis 1h theo URL hash → request lặp trong ngày không tốn Playwright.
Service này gánh phần rủi ro nhất — network, browser, timeout. Browser pool là micro-optimization ROI rất cao.
05 · Services · 3/5

SEO Analyzer

gRPC :50053 · DB seo_analyzer

Rule engine — 22 rules trên 7 categories.

What · trách nhiệm

  • Consume analyze.start
  • Chạy 22 rule theo interface ISeoRule
  • Category score = weighted avg; overall score
  • Persist RuleResult (22 rows / audit)
  • Pub analyze.done
  • Admin gRPC: list rules, update weight live

Why · quyết định thiết kế

  • Open/Closed Principle — ISeoRule + RuleRegistry. Thêm rule = 1 file mới + register, không đụng engine.
  • Weight lưu trong DB (không hard-code) → admin chỉnh weight không cần deploy.
  • 22 rule / 7 category: meta (4), headings (2), images (2), links (3), content (1), performance (1), technical (9).
Đây là ví dụ sống của OCP trong code thực. Hội đồng hay hỏi "thêm rule mới làm thế nào" — trả lời: 1 file, 10 phút, không cần biết phần còn lại.
05 · Services · 4/5

Keyword Analyzer

gRPC :50054 · stateless

Phân tích từ khoá theo target keyword người dùng nhập.

What · trách nhiệm

  • Consume keyword.start
  • Tokenize với stopwords Việt + Anh
  • Term Frequency (TF) cho top keywords
  • Density check: healthy = 1–3%
  • Placement check: title · H1 · URL · 100 từ đầu
  • Verdict: missing / under-optimized / optimal / stuffed
  • Pub keyword.done

Why · quyết định thiết kế

  • Service nhẹ nhất — ví dụ chuẩn của Single Responsibility.
  • Stateless — không có DB riêng, cache Redis kết quả; scale ngang tự do.
  • Replace-able — nếu sau này thay bằng AI-based keyword scoring, chỉ cần rewrite service này.
Minh chứng rõ ràng cho lợi ích của microservice: nếu cần đổi logic keyword scoring sang AI, chỉ sửa service này mà không đụng phần còn lại.
05 · Services · 5/5

Report

HTTP :3004 · gRPC :50055 · DB seo_report

Tổng hợp, sinh PDF, quản lý share link.

What · trách nhiệm

  • Sub analyze.done + keyword.done + crawl.done
  • WaitForBothService đếm 2/2 → enqueue report.start (self)
  • Aggregate: 0.7 × analyzer + 0.3 × CWV
  • Persist Report + pub report.done / audit.completed
  • PDF = Playwright render + Handlebars template
  • Share link = randomBytes(32).toString('hex') (64 chars)

Why · quyết định thiết kế

  • WaitForBothService = Join pattern: 2 async stream gặp nhau qua Redis counter. Không có nó → hoặc poll (waste), hoặc race condition (thiếu data).
  • Self-enqueue report.start → giãn áp lực; retry/DLQ miễn phí từ BullMQ.
  • Playwright tái dùng → không thêm tool PDF mới, share browser pool với crawler.
Đây là chỗ technical sâu nhất. WaitForBothService là pattern "join" cổ điển nhưng áp dụng cho microservice qua Redis counter — đáng dừng 1 phút.

Queues vs Topics khác nhau ở đâu? Queue đảm bảo exactly-one consumer xử lý + retry/DLQ. Topic broadcast fire-and-forget, subscriber nào offline lúc đó là mất event.
Nhấn mạnh: 4 queue cho "làm việc" (có retry/DLQ), 7 topic cho "thông báo" (không persist). Chọn sai cơ chế là sai kiến trúc. Ví dụ: nếu dùng pub/sub cho crawl.start thì job nào fail là mất luôn.

08 · Communication

3 cơ chế giao tiếp — dùng đúng việc

Cơ chếDùng khiVí dụ
gRPC
synchronous		 Cần response ngay, type-safe request/reply Gateway → Report GetReport, GeneratePdf, CreateShareLink
BullMQ
async queue		 Long-running, cần retry, fan-out, DLQ crawl.start → analyze.start + keyword.start → report.start
Pub/Sub
event broadcast		 Choreography, nhiều subscriber, không cần delivery guarantee Progress updates, *.done events, audit completion
Kỷ luật kiến trúc: Service boundary = Postgres DB boundary; chỉ Gateway public HTTP; không thêm cơ chế giao tiếp khác.
Nhiều project lạm dụng REST cho mọi thứ — đó là anti-pattern. Mỗi cơ chế giải quyết 1 vấn đề khác nhau, trade-off khác nhau.

Được gì

  • Loose coupling — schema Analyzer đổi không kéo migration Gateway
  • Scale độc lập — Analyzer ghi nhiều có thể tune riêng
  • Failure isolation — DB analyzer down, user vẫn login được
  • Compliance-ready — phân quyền theo nhóm dữ liệu

Trade-off

  • Không JOIN cross-service → phải aggregate ở application layer
  • Query analytics ("top user có score cao") cần ETL riêng
  • Transaction phân tán phải dùng saga + compensation
Hội đồng hay hỏi "sao không 1 DB cho đơn giản" → trả lời: coupling giết khả năng scale/deploy độc lập. Cái giá là aggregator ở app layer. Đây là trade-off có chủ đích.

11 · Key Takeaways

5 điểm nếu chỉ nhớ được 5 thứ

  1. Database-per-service là ràng buộc kỷ luật, không phải trang trí — mất JOIN để được decoupling.
  2. Hybrid orchestration + choreography — Gateway cứng khi khởi đầu, workers mềm khi xử lý.
  3. 22 SEO rules theo Open/Closed — thêm rule = 1 file mới, không chạm engine.
  4. WaitForBothService = Join pattern — 2 async streams gặp nhau qua Redis counter.
  5. Dùng đúng cơ chế — BullMQ khi cần retry/DLQ; Pub/Sub khi cần broadcast; gRPC khi cần sync type-safe.
Nhắc lại 5 điểm để đóng gói. Mỗi điểm là 1 quyết định thiết kế có chủ đích.
12 · Self-critique

Điểm yếu biết trước & roadmap

Hạn chế

  • Redis là SPOF — queue + pub/sub + cache + rate-limit cùng phụ thuộc
  • Không distributed tracing — debug cross-service phải grep log
  • Không timeout WaitForBothService → counter kẹt 1/2 → audit treo
  • Không saga compensation — keyword fail sau 3 retry là không có cơ chế rollback audit
  • Proto evolution chưa lint → breaking change có thể lọt vào PR
  • Observability dừng ở logs — chưa có Prometheus metrics

Roadmap

  • Ngắn hạn: Public API + API key · timeout WaitForBothService · tăng test cho Report
  • Trung hạn: OpenTelemetry + Prometheus · proto-lint enforce backward compat · Redis Sentinel
  • Dài hạn: Multi-page crawl (sitemap) · backlink check (Common Crawl) · AI-powered recommendations qua packages/seo-ai-core
Nguyên tắc trình bày: kể điểm yếu trước khi hội đồng hỏi ra — thể hiện mình hiểu hệ thống chứ không build theo template.
